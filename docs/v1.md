# V1 Local Video Storage

## Expectation

Simple upload and retrieval of video content.

CLI -> API -> Storage

## State

- Spring Boot
- Local filesystem
- Multipart/form-data
- UUID-based file identification

## Questions

### Upload

- What happens if the client aborts the connection during upload?
- Is a partially written file ever considered valid?
- How do we clean up incomplete uploads?
- Should uploads be atomic?

### Download

- What happens if the client aborts the connection during download?
- Should the server continue reading the file?
- How should HTTP Range requests behave?

### Metadata

- How are original filenames retained?
- Where is the MIME type stored?
- How is file size obtained?
- What identifies a video?

### Metadata questions

- Should metadata live beside the video or separately?
- Should metadata be written before or after the video?
- What happens if metadata is written but the video is not?
- What happens if the video exists but metadata is missing?
- Should metadata be regenerated from the file?
- Which metadata is authoritative?
- How should metadata updates be synchronized with the filesystem?
- How should metadata be indexed when the number of videos grows?

### Storage

- How is the storage path determined?
- What happens if the filesystem becomes unavailable?
- What happens if two uploads produce the same content?

### Problems

- Multipart uploads are limited to 1 MB by default.
  - Possible solutions:
    - Increase the multipart file size limit through `application.properties`.
    - Implement application-level chunked uploads.
  - Trade-offs:
    - Increasing the limit:
      - Simple to implement.
      - Higher resource consumption for large uploads.
      - Still relies on a single HTTP request.
      - An interrupted upload requires restarting the entire request.
    - Chunked uploads:
      - More complex implementation.
      - Requires chunk identification and ordering.
      - Requires validation of missing/duplicated chunks.
      - Requires temporary storage for incomplete uploads.
      - Requires a mechanism to finalize and assemble the file.
      - Interrupted uploads can potentially be resumed.
  - My decision:
    - Implement application-level chunked uploads.
      - This introduces additional complexity, but provides better behavior for large files and concurrent clients.
      - Failed uploads can be retried from the last successfully uploaded chunk instead of restarting the entire upload.
      - Uploads can be resumed after temporary connection failures.
      - The implementation will initially prioritize correctness and reliability over upload throughput.

Improve the V1 storage architecture by introducing persistent video
metadata and a reliable upload lifecycle.

The system should support:

- Resumable chunked uploads.
- Persistent video metadata.
- Reliable detection of incomplete uploads.
- Atomic publication of completed videos.
- Recovery of in-progress and completed uploads after application restarts.
- Separation between video metadata and video content.
